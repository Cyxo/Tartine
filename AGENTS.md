# AGENTS.md

## Stack
- Java only. Toolchains via mise (`mise.toml`: Corretto 27 + Gradle 9.8.1); run everything through `mise exec -- gradle ...` so the pinned JDK is used. Scripts under `scripts/` are POSIX bash (Mac/Linux); Windows uses the mise `run_windows` pwsh twins (`scripts/*.ps1`). A Gradle wrapper is committed for IDEs/CI — keep its version in sync with mise's `gradle` pin.
- Java 21 compatibility floor, enforced as `options.release = 21` in `build.gradle` (raised from 14 per the 2026-10 audit; our sources may be new-JDK-built on Corretto 27 but must stay Java-21-loadable). Do not use language features or JDK APIs introduced after Java 21. Verify with `javap -verbose` / `jdeps` if unsure.
- Launch floor (follow-up audit, decided 2026-10-19): runtime launches require JDK 25+ LTS — bundled later; until then a present JDK ≥25 is required. The launcher flags already refuse older JVMs (`--sun-misc-unsafe-memory-access` exists only from JDK 24), so "Java 21" was never a launch floor; release=21 remains the bytecode/source compatibility floor only. Dev pin stays Corretto 27 via mise (non-LTS is fine for building; launches target 25 LTS).

## Repo state
- Layout: `src/main/java/tartine/` (`Main`, `apk/`, `config/`, `dex/`, `vm/`, `runtime/`, `graphics/`, `fw/`), `framework/` (Gradle module: generated android.* skeletons + Java behavior),
`src/test/java/` (JUnit 5 suite), `settings.gradle`/`build.gradle` (+ committed Gradle wrapper — mise still pins the version; keep the two in sync), `build/` (ignored output). `tools/` (dev-time CLI oracles, gitignored — fetch with `mise run fetch-tools`), `apks/` (ignored local fixtures), `THIRD-PARTY.md` (versions/licenses). Deps resolve from Maven Central + Google Maven (`google()` in `build.gradle`; smali-dexlib2 publishes only there) via Gradle; nothing vendored under `libs/`.
- Verify: `sh scripts/verify.sh` (all platforms). Runs `mise install` (idempotent) then `gradle test`.
- Prefer `mise run <task>` (`fetch-tools`/`test`/`build`/`apk`/`run`/`gui`/`dump`/`fw-gen`, see `mise tasks ls`): `apk`/`run`/`gui`/`dump` launch the last build via direct `java`, no recompile when unchanged. Run `mise trust` after editing `mise.toml` (edits revoke trust).
- Single test: `mise exec -- gradle test --tests "tartine.apk.*"`.

## Goal
- Run Android APKs natively on desktop (Windows/Mac/Linux): no QEMU, no container/VM image (i.e. not Anbox/Waydroid/Emulator). Wine-like translation layer instead.
- Reference prior art before designing: GitLab `android_translation_layer/android_translation_layer` (bionic_translation + art_standalone, Linux-only).

## APK to execution pipeline
- APK is a signed ZIP: `AndroidManifest.xml` (binary XML, use `aapt2 dump`/`apktool`), `classes.dex` (+`classes2.dex`… multidex), `resources.arsc`, `res/`, `assets/`, `lib/<abi>/*.so`, `META-INF/`.
- DEX != JVM bytecode, never load it directly: register-based (frames fixed at creation, up to v65535, typically <16), 16-bit code units, whole-app shared pools (string/type/proto/field/method); JVM is stack-based per-class files with ~different opcodes. Spec: `source.android.com/docs/core/runtime/dalvik-bytecode`, `/dex-format`.
- Dalvik (old JIT) is superseded by ART (AOT via on-device `dex2oat` + JIT/GC); both execute DEX so Dalvik-targeted apps run on ART with edge cases. Stock ART is not desktop-portable: it depends on Bionic, Binder IPC, Zygote fork model, system services.
- VM strategy (decided Step 3): interpreter-first. `tartine.vm.Interpreter` executes our IR directly; unknown opcodes and unimplemented methods throw `VmException` naming the gap, so each failure is the next task. The android.* framework must be reimplemented either way; the interpreter grows one opcode/test at a time, while translation (spiked via ASM 9.6 on the fixture: runs, but first attempt died in the JVM verifier, and type inference/frames/exceptions remain untouched) adds pitfalls without removing framework work. Audit 2026-10 revision (user-approved): framework behavior migrates into real Java classes (see "Framework in Java" below) and the translation spike runs right after the first Activity renders instead of "after apps run".
- `android.jar` bodies are all `throw new RuntimeException("Stub!")` (verified via `javap -c`): reuse it for hierarchy/signatures/constants only, never behavior. Devices have no `android.jar` — they ship `framework.jar` with real DEX, but it needs natives/Binder/preloaded state and is not reusable on desktop; don't go there. Parse the LOCAL SDK jar matching the APK (`<sdk>/platforms/android-<targetSdk>/android.jar`); Maven's `com.google.android:android` artifact is API 16 and useless. True constants (`View.VISIBLE = 0`) read fine; runtime fields (`VERSION.SDK_INT`) have no value in the jar and must be supplied by us. Even pure-Java utils (SparseArray) drag `com.android.internal` deps — port their semantics as host builtins, don't compile AOSP sources. (`d8` exists in local build-tools; compiling framework Java to DEX stays deferred — it needs full opcodes + JNI answers anyway.)
- Whichever VM is chosen, `android.jar` is stubs only: Activity/lifecycle, `AssetManager`/resources, Binder-based services, Bionic/libc shims, and `lib/<abi>` native libs (ARM `.so` needs same-arch APK or binary translation) must each be reimplemented or explicitly stubbed. Host builtins (`String`, atomics, ...) carry value semantics. (The "framework objects allocate as placeholders with no-op `<init>`" model below predates the 2026-10 audit adoption — it is what we run today; the Framework-in-Java section supersedes it as we migrate.)
- `java.*` calls fall back to host reflection (table first for normalizations like boolean→int, then reflective dispatch on host objects only; model objects never cross). Scope is deny-by-default (landed 2026-10-19): an explicit allowlist of modules/classes may cross (follow-up audit 2026-10-19, replacing the 9-class blocklist — it is passable via `Class.forName("java.lang.Runtime")` + reflective `invoke`, since `java.lang.Class` itself must stay reachable; pin the bypass with a test before and after). The landed shape: allowlist prefixes `java.lang` + `reflect` + `annotation`, `java.util` + `concurrent`(+`function`/`stream`)+`regex`, `java.text`, `java.math` — with the 9-class deny set (+`ProcessHandle`) overriding inside them; `java.io`/`java.nio`/`java.net` stay off the list (the `File` bridge builtins route through `tartine.runtime.Vfs` and fail closed); static calls gate the defining class, instance calls gate the receiver's runtime class (java.* receivers only — interpreter-internal models like `BoxedZero` stay reachable); `Class.forName`/`loadClass` resolve the dex+framework universe only, so `forName("java.lang.Runtime")` answers `ClassNotFoundException` (pinned by the fixture's `forNameDenied`). Allocation, methods, and statics resolve reflectively per call with no method cache — hand-write only behavioral mismatches, with a fixture test proving each.
- Interpreter architecture (follow-up audit 2026-10-19): the file grew to ~8.1k lines with uncached reflection dispatch; split it (dispatch, reflection bridge, builtins registry, frame plumbing) and move to a pre-resolved IR — method/field/type references resolve once into cached host targets. The translation spike builds on the same resolution layer.

## Framework in Java (2026-10 audit adoption, user-approved)
- The android.* framework is real Java classes, not string-keyed builtins inside `tartine.vm.Interpreter`. Skeletons carry exact signatures from the LOCAL SDK `android.jar` (generator, dev-time) into a `framework` Gradle module; every unimplemented body throws `UnsupportedOperationException("Tartine: not implemented: <signature>")` — the gap-driven loop survives verbatim. Behavior is implemented in plain Java there; AOSP/Robolectric/layoutlib stay read-only references (never runtime deps).
- The interpreter becomes the adapter: (1) guest allocations of android.* classes construct host framework objects (fields move out of `VmObject` HashMap placeholders as each class ports); (2) framework dispatch checks guest override first (runs DEX), then reflective host invocation, else throws the skeleton's named gap; (3) guest classes extending android.* get generated peers whose overridden methods call back into the interpreter.
- Builtins stop growing: new framework behavior is written in the framework module only. Existing ~685 string-keyed builtins (Interpreter, ~8.1k lines as of the 2026-10-19 follow-up audit) port opportunistically; delete a registration as soon as its class ports and tests prove parity.
- Never port framework behavior from memory. Read the AOSP source first and cite the exact file + method in the porting comment (see `ViewGroup.getChildAt`). Stale-memory ports are how `getChildAt` regressed: current AOSP returns null out of range; older releases threw. When memory and source disagree, source wins; pin the parity with a test.
- Local source refs (read-only, machine-local, never commit absolute local paths into tracked docs — they leak the username): the OpenCode temp root's `refs\` folder, i.e. `%LOCALAPPDATA%\Temp\opencode\refs\` — `androidx\` (github.com/androidx/androidx, sparse: activity, annotation, collection, core, customview, lifecycle, savedstate, compose/{ui,runtime,foundation}) and `aosp-frameworks-base\` (github.com/aosp-mirror/platform_frameworks_base, sparse: core/java/android/{view,graphics,content,os,app,window,widget} + core/java/com/android/internal/policy). Shallow blobless `--sparse` clones, `core.autocrlf=false`. The dir sits under the opencode temp root, so the OS may purge it — re-clone if missing.
- Migration order should follow the probe walls (measure → layout → draw): port the class a wall needs instead of adding another builtin.
- Generator state (2026-10-17, committed): `SkeletonGen` seeds `android/graphics/Paint`, closure-follows any class `FwIndex.find` resolves from `android.jar` EXCEPT `java.*`/`javax.*` (host JDK owns those; guest passthrough reflects them), emits class/method-level generic Signatures (bare type params, bounds consumed only; method `S::Iface` empty-class-bound form handled), skips enum `<init>`s (constants clauses call the implicit one; a re-emitted UOE body would break `<clinit>`) and compiler-generated `values()`/`valueOf`, keeps `final` only on static finals with ConstantValue, and skips valueless fields inside interfaces (always implicitly final). Deletion+regen is the way to refresh (additive on disk).
- Translation spike (trigger MET 2026-10-19 — first Activity renders and the first frame blits, `f4f113c`; start stays user-gated after the follow-up audit): ASM translator emitting classfile version 49 (no StackMapTable — the old type-inferencing verifier covers it; v50 without stackmaps also still fails over, verified 2026-10 on current HotSpot), dex2jar/Enjarify as oracles, `COMPUTE_FRAMES` with a DEX-hierarchy `getCommonSuperClass` as the fallback frame strategy. Adopt if the translated fixture runs `onCreate` against the Java framework; otherwise stay interpreter and keep porting builtins to Java. Keep the interpreter as probing/debug tool even after adoption.
- Verified fallback supports the design: JVM still mandates type-inference verification for v50 classfiles (JVMS §4.10; `FailOverToOldVerifier` merely deprecated in JDK 13), so stackmap-free translated classes verify on current JDKs.
- Scope cap (document in README): pure-DEX apps only. ARM `.so` libs (Bionic) can't load on desktop JVMs — Flutter, most games and native-code apps excluded until binary translation exists.
- References only, no runtime deps: Robolectric shadow patterns (Loopers/system services), AOSP layoutlib (native text/gfx), Paparazzi as a possible golden-frame oracle in a separate dev-time module.
- Deferred housekeeping (ordered later, from the 2026-10 audits): split AGENTS.md design sections into docs/architecture.md + ADRs; small committed fixture APK so fresh clones can probe; unify script wording; move root `icon.png`/`icon.svg`/`logo.png` into `docs/assets/`; move the generator (`SkeletonGen`, `Sdk`, `FwIndex`) out of the runtime source set into a tools module; unify `tartine.fw` across the two modules (framework module owns it; the vm reaches the index through a narrow seam); add tests inside `framework/`; decouple Skija from android.* files (first step: replace `SkiaPresenter`'s `setAccessible` seam with a hidden public factory; better: layoutlib-style delegates so tests run native-free and the backend stays swappable); import convention — FQNs only where names genuinely clash (Skija vs `android.graphics` Canvas/Paint/Path/Matrix/Rect/Region/Typeface/Bitmap), generator gains a clash-aware import manager, one-time shorten pass on existing files; runtime free of a local Android SDK (FwIndex derived from the framework jar at build time).
- Theme sync (future, user idea 2026-10-19): follow the desktop OS's native light/dark theme — Windows registry (`AppsUseLightTheme`), macOS `AppleInterfaceStyle`-style defaults, Linux XDG settings portal (`org.freedesktop.appearance` `color-scheme`) — reporting it into the guest `Configuration` (`uiMode` night mode) so Compose picks the dark palette; where the OS exposes an accent color (Windows accent color, macOS accent-color, portal variants), consider seeding an accent-derived palette against the `system_accent*` baseline. `config.properties` gets a `theme` key (`light|dark|auto`) that pins the choice explicitly; `auto` = host default.

## Virtual filesystem (decided 2026-10)
- Seam: `tartine.runtime.Vfs` maps guest absolute paths to host paths; unmapped paths resolve to `null` and the future java.io/java.nio.file guest bridge must fail closed (deny), never fall back to the host cwd.
- Root = app data, not config: Windows `%LOCALAPPDATA%\Tartine`, macOS `~/Library/Application Support/Tartine`, Linux `$XDG_DATA_HOME/tartine` (default `~/.local/share/tartine`); `TARTINE_HOME` env or `tartine.home` property override everything. The HOST config file sits at this root too (`config.properties`, loaded once at startup by `tartine.config.HostConfig`): host-only, never guest-mapped — the mount rules below keep it hidden from guests. Keys today: `color.<name|id>` — canonical `android.R$color` constant names (the spelling ROM overlays customize; resolved by the generated `tartine.fw.SystemResourceNames` table, extracted from the LOCAL jar next to the values baseline) or numeric ids, both beating the `tartine.fw.SystemColors` baseline — and `font.families` (preferred desktop families; config > `TARTINE_FONT_FAMILIES` env > built-in list). README documents every knob (see Commits).
- Guest mounts (longest prefix wins): `/data/data/<pkg>` and `/data/user/0/<pkg>` (incl. `files|cache|databases|shared_prefs`) → `<root>/data/<pkg>`; `/data/app/<pkg>` → `<root>/apps/<pkg>` (installed `base.apk` / guest-visible sourceDir); `/data/local/tmp` → `<root>/tmp`. `/sdcard` mounts follow the tiers below (decision 2026-10-19). `/system`, `/proc`, `/dev`... stay unmapped.
- Traversal (`..`) and Windows-unsafe segments (drive letters, reserved device names, `:` streams) are denied at the seam (tested in `VfsTest`).
- Shared storage, tiered (follow-up audit 2026-10-19, user-approved; supersedes "sdcard = real home read-write Wine-style"):
  1. Default: a private virtual card at `<root>/sdcard`, shared by all apps, seeded with the standard folders (`Download`, `Documents`, `Pictures`, `DCIM`, `Music`, `Movies`).
  2. Opt-in: user-mapped folders (e.g. `/sdcard/Download` → `~/Downloads`), each flagged read-only or read-write, globally or per app.
  3. File pickers: `ACTION_OPEN_DOCUMENT`/`ACTION_OPEN_DOCUMENT_TREE`/`ACTION_CREATE_DOCUMENT` map to native desktop dialogs for everything else (backend to verify when built — the audit believes LWJGL ships nfd/tinyfd bindings); grants stored per app (scoped-storage apps don't expect broad sdcard access).
  Whole-home mounting survives only as an explicit advanced option — read-only by default, with a warning, for Wine-style behavior.
  Seam rules for every mapped folder: the mount must exclude Tartine's own root; symlink/junction targets are realpath-checked back inside the mount (`..` checks alone are not enough); obviously dangerous roots (`/`, drive roots, the Tartine root) are refused; the read-only flag is enforced; configuration lives in a config file with `TARTINE_SDCARD` or a CLI flag as overrides.

## Graphics ("windows") mapping
- Android path, bottom-up: `Canvas` (Skia 2D) / GLES-via-EGL(`ANativeWindow`) / Vulkan → `Surface` (BufferQueue producer) → `SurfaceFlinger` (VSync-driven system compositor, HWC/OpenGL) → display. `WindowManager` owns Window/View lifecycle, z-order, transforms, and hands layers (`Surface`+`SurfaceControl`) to SurfaceFlinger. `SurfaceView` gets its own layer (isolated); `TextureView` composites inside app GLES. Spec: `source.android.com/docs/core/graphics/architecture`, `/surfaceflinger-windowmanager`.
- Desktop mapping: reimplement a minimal WindowManager + SurfaceFlinger-lite — one Android Window/Surface maps to one desktop window; bridge BufferQueue/gralloc to desktop buffers; pace frames off desktop VSync (Choreographer equivalent).
- Rendering backend: prefer Skia (same engine backing Android `Canvas`, cross-platform C++) or LWJGL + GLES via ANGLE for the GLES path. Do not use JavaFX as the compositor: it is a widget toolkit at the wrong layer and cannot faithfully host Surfaces/HWC semantics; low-level windowing (GLFW/SDL) + GL/Vulkan is the correct substrate. Audit 2026-10 note: the Java route to Skia is the Skija/JetBrains Skiko bindings (Apache-2.0 family — verify license row before adding to THIRD-PARTY); LWJGL only supplies windowing + GL, not a 2D engine. Threading (follow-up audit, decided 2026-10-19, supersedes "Looper drives the GLFW pump"): a dedicated host UI thread owns GLFW/windowing and presents surfaces behind a `HostDisplay` interface — on macOS that thread must be the process main (our `-XstartOnFirstThread` script arrangement already guarantees it); guest app code runs on its own main-looper thread and posts frame updates through `HostDisplay` — the Choreographer→SurfaceFlinger shape — never calling GLFW. Decision 2026-10-18 (draw chain): UI Canvas draws rasterize through Skia via Skija (`io.github.humbleui:skija-*` 0.143.18), first bridge = Skia software bitmap blitted through the LWJGL GL context; **no pure-GL drawing of UI content** — LWJGL stays windowing, blit, and the future GLES path (ANativeWindow-style app content only).
- First bridge landed (2026-10-19, `f4f113c`): `DesktopWindow` uploads the first-draw Skia raster as one GL texture (N32 BGRA byte order + `GL_UNSIGNED_BYTE`, one copy; opaque frames present as-is) and letterboxes it per VSync-paced swap; resizing recomputes the letterbox. Next: Choreographer-driven redraws posting through `HostDisplay`.
- Window icon landed (2026-10-19): `tartine.apk.AppIcon` resolves the manifest `android:icon`/`roundIcon` through a new `ResourceTable` (binary `resources.arsc` reader) and renders 16/32/48 RGBA buffers for `glfwSetWindowIcon`: rasters decode via Skija (straight-alpha un-premultiply), `<adaptive-icon>`/`<vector>` convert to SVG (groups/paths/gradients/clip-paths; AOSP VectorDrawable group contract: scale→rotate→translate, pivot-wrapped) and render via jsvg (`com.github.weisj:jsvg` 2.2.0, MIT) with aapt2 `$name__N` inline-gradient files; `BinaryXml` now exposes typed attribute `dataType`/`data`. Unconverted sources (`<inset>`, `?attr`, sweep gradients, layer-lists) log `icon:` gap lines and fall back to the OS default icon; `MeshResourceTableTest`-style unit fixtures live in `Fixtures.java` under `src/test`.

## Installation, daemon, IPC (design notes recorded 2026-10-19 from the follow-up audit)
- One host JVM per guest app (one Android process ≈ one JVM); app processes start on demand, never at boot.
- Installation happens on first run of an APK: verify signatures with `apksig` (v1/v2/v3 schemes), unpack into `<root>/apps/<pkg>`, record metadata in a package database (package name, `versionCode`, signing certificate).
- Updates follow Android's install rules: `versionCode` must increase and the signing certificate must match; be wary of v3 cert-lineage rotation when deciding matches.
- Daemon: a per-user, unprivileged background process owning install state and launch decisions; IPC over Unix-domain sockets (JDK 16+ AF_UNIX, included on Windows 10+).
- Shortcuts (Start menu / Finder / `.desktop`) point at the daemon so it can locate and persist the right app JVM and store per-app grants.
- Startup cost: generate AppCDS archives per app at install time to cut each app JVM's class-loading latency.
- Cross-process services: a Binder-style `Parcel` serialization seam, implemented in-process first; the cross-JVM transport rides the daemon socket later.

## Commits
- Conventional Commits required (`feat:`, `fix:`, `chore:`, etc.). No other convention is defined.

## Third-party policy
- Reuse-first: prefer OSS/AOSP over hand-rolled (dexlib2 for DEX, baksmali/apktool CLIs as decode oracles, dex2jar/Enjarify as translation oracles, LWJGL3 for windowing/GLES, AOSP ART/Skia as reference only).
- Download CLI oracles into `tools/` via `mise run fetch-tools` (gitignored, never on the runtime classpath); record version + URL + license in `THIRD-PARTY.md`. Compile deps are declared in `build.gradle` (Maven Central + Google Maven; see Repo state), not vendored.
- Only permissive licenses in the runtime path (Apache-2.0/BSD/MIT); keep license texts, never strip copyrights. Our sources stay at the `--release 21` floor regardless of what a vendored jar targets.
