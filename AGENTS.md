# AGENTS.md

## Stack
- Java only. Toolchains via mise (`mise.toml`: Corretto 27 + Gradle 9.8.1); run everything through `mise exec -- gradle ...` so the pinned JDK is used. Scripts under `scripts/` are POSIX bash (Mac/Linux); Windows uses the mise `run_windows` pwsh twins (`scripts/*.ps1`). A Gradle wrapper is committed for IDEs/CI — keep its version in sync with mise's `gradle` pin.
- Java 21 compatibility floor, enforced as `options.release = 21` in `build.gradle` (raised from 14 per the 2026-10 audit; our sources may be new-JDK-built on Corretto 27 but must stay Java-21-loadable). Do not use language features or JDK APIs introduced after Java 21. Verify with `javap -verbose` / `jdeps` if unsure.

## Repo state
- Layout: `src/main/java/tartine/` (`Main`, `apk/`, `dex/`, `vm/`, `runtime/`, `graphics/`, `fw/`), `framework/` (Gradle module: generated android.* skeletons + Java behavior),
`src/test/java/` (JUnit 5 suite), `settings.gradle`/`build.gradle` (+ committed Gradle wrapper — mise still pins the version; keep the two in sync), `build/` (ignored output). `tools/` (dev-time CLI oracles, gitignored — fetch with `mise run fetch-tools`), `apks/` (ignored local fixtures), `THIRD-PARTY.md` (versions/licenses). Deps resolve from Maven Central via Gradle; nothing vendored under `libs/`.
- Verify: `sh scripts/verify.sh` (all platforms). Runs `mise install` (idempotent) then `gradle test`.
- Prefer `mise run <task>` (`fetch-tools`/`test`/`build`/`apk`/`run`/`gui`/`dump`/`fw-gen`, see `mise tasks ls`): `apk`/`run`/`gui`/`dump` launch the last build via direct `java`, no recompile when unchanged. Run `mise trust` after editing `mise.toml` (edits revoke trust).
- Single test: `mise exec -- gradle test --tests "tartine.apk.*"`.

## Goal
- Run Android APKs natively on desktop (Windows/Mac/Linux): no QEMU, no container/VM image (i.e. not Anbox/Waydroid/Emulator). Wine-like translation layer instead.
- Reference prior art before designing: GitLab `android_translation_layer/android_translation_layer` (bionic_translation + art_standalone, Linux-only).

## APK to execution pipeline
- APK is a signed ZIP: `AndroidManifest.xml` (binary XML, use `aapt2 dump`/`apktool`), `classes.dex` (+`classes2.dex`… multidex), `resources.arsc`, `res/`, `assets/`, `lib/<abi>/*.so`, `META-INF/`.
- DEX != JVM bytecode, never load it directly: register-based (frames fixed at creation, up to v65535, typically <16), 16-bit code units, whole-app shared pools (string/type/proto/field/method); JVM is stack-based per-class files with ~different opcodes. Spec: `source.android.com/docs/core/runtime/dalvik-bytecode`, `/dex-format`.
- Dalvik (old JIT) is superseded by ART (AOT via on-device `dex2oat` + JIT/GC); both execute DEX so Dalvik-targeted apps run on ART with edge cases. Stock ART is not desktop-portable: it depends on Bionic, Binder IPC, Zygote fork model, system services.
- VM strategy (decided Step 3): interpreter-first. `tartine.vm.Interpreter` executes our IR directly; unknown opcodes and unimplemented methods throw `VmException` naming the gap, so each failure is the next task. The android.* framework must be reimplemented either way; the interpreter grows one opcode/test at a time, while translation (spiked via ASM 9.6 on the fixture: runs, but first attempt died in the JVM verifier, and type inference/frames/exceptions remain untouched) adds pitfalls without removing framework work. Audit 2026-10 revision (user-approved): framework behavior migrates into real Java classes (see "Framework in Java" below) and the translation spike runs right after the first Activity renders instead of "after apps run".
- `android.jar` bodies are all `throw new RuntimeException("Stub!")` (verified via `javap -c`): reuse it for hierarchy/signatures/constants only, never behavior. Devices have no `android.jar` — they ship `framework.jar` with real DEX, but it needs natives/Binder/preloaded state and is not reusable on desktop; don't go there. Parse the LOCAL SDK jar matching the APK (`<sdk>/platforms/android-<targetSdk>/android.jar`); Maven's `com.google.android:android` artifact is API 16 and useless. True constants (`View.VISIBLE = 0`) read fine; runtime fields (`VERSION.SDK_INT`) have no value in the jar and must be supplied by us. Even pure-Java utils (SparseArray) drag `com.android.internal` deps — port their semantics as host builtins, don't compile AOSP sources. (`d8` exists in local build-tools; compiling framework Java to DEX stays deferred — it needs full opcodes + JNI answers anyway.)
- Whichever VM is chosen, `android.jar` is stubs only: Activity/lifecycle, `AssetManager`/resources, Binder-based services, Bionic/libc shims, and `lib/<abi>` native libs (ARM `.so` needs same-arch APK or binary translation) must each be reimplemented or explicitly stubbed. Host builtins (`String`, atomics, ...) carry value semantics. (The "framework objects allocate as placeholders with no-op `<init>`" model below predates the 2026-10 audit adoption — it is what we run today; the Framework-in-Java section supersedes it as we migrate.)
- `java.*` calls fall back to host reflection (table first for normalizations like boolean→int, then reflective dispatch on host objects only; `java.*`-only scope with a blocklist; model objects never cross). Allocation, methods, and statics resolve reflectively — hand-write only behavioral mismatches, with a fixture test proving each.

## Framework in Java (2026-10 audit adoption, user-approved)
- The android.* framework is real Java classes, not string-keyed builtins inside `tartine.vm.Interpreter`. Skeletons carry exact signatures from the LOCAL SDK `android.jar` (generator, dev-time) into a `framework` Gradle module; every unimplemented body throws `UnsupportedOperationException("Tartine: not implemented: <signature>")` — the gap-driven loop survives verbatim. Behavior is implemented in plain Java there; AOSP/Robolectric/layoutlib stay read-only references (never runtime deps).
- The interpreter becomes the adapter: (1) guest allocations of android.* classes construct host framework objects (fields move out of `VmObject` HashMap placeholders as each class ports); (2) framework dispatch checks guest override first (runs DEX), then reflective host invocation, else throws the skeleton's named gap; (3) guest classes extending android.* get generated peers whose overridden methods call back into the interpreter.
- Builtins stop growing: new framework behavior is written in the framework module only. Existing ~685 string-keyed builtins (Interpreter, ~7.2k lines as of 2026-10-17) port opportunistically; delete a registration as soon as its class ports and tests prove parity.
- Never port framework behavior from memory. Read the AOSP source first (Google-maintained GitHub mirror `aosp-mirror/platform_frameworks_base`, or `googlesource.com`, or the SDK `sources/<api>/` packages) and cite the exact file + method in the porting comment (see `ViewGroup.getChildAt`). Stale-memory ports are how `getChildAt` regressed: current AOSP returns null out of range; older releases threw. When memory and source disagree, source wins; pin the parity with a test.
- Migration order should follow the probe walls (measure → layout → draw): port the class a wall needs instead of adding another builtin.
- Generator state (2026-10-17, committed): `SkeletonGen` seeds `android/graphics/Paint`, closure-follows any class `FwIndex.find` resolves from `android.jar` EXCEPT `java.*`/`javax.*` (host JDK owns those; guest passthrough reflects them), emits class/method-level generic Signatures (bare type params, bounds consumed only; method `S::Iface` empty-class-bound form handled), skips enum `<init>`s (constants clauses call the implicit one; a re-emitted UOE body would break `<clinit>`) and compiler-generated `values()`/`valueOf`, keeps `final` only on static finals with ConstantValue, and skips valueless fields inside interfaces (always implicitly final). Deletion+regen is the way to refresh (additive on disk).
- Translation spike (after the first Activity renders, was "after apps run"): ASM translator emitting classfile version 49 (no StackMapTable — the old type-inferencing verifier covers it; v50 without stackmaps also still fails over, verified 2026-10 on current HotSpot), dex2jar/Enjarify as oracles, `COMPUTE_FRAMES` with a DEX-hierarchy `getCommonSuperClass` as the fallback frame strategy. Adopt if the translated fixture runs `onCreate` against the Java framework; otherwise stay interpreter and keep porting builtins to Java. Keep the interpreter as probing/debug tool even after adoption.
- Verified fallback supports the design: JVM still mandates type-inference verification for v50 classfiles (JVMS §4.10; `FailOverToOldVerifier` merely deprecated in JDK 13), so stackmap-free translated classes verify on current JDKs.
- Scope cap (document in README): pure-DEX apps only. ARM `.so` libs (Bionic) can't load on desktop JVMs — Flutter, most games and native-code apps excluded until binary translation exists.
- References only, no runtime deps: Robolectric shadow patterns (Loopers/system services), AOSP layoutlib (native text/gfx), Paparazzi as a possible golden-frame oracle in a separate dev-time module.
- Deferred housekeeping (after the fixture reaches draw): split AGENTS.md design sections into docs/architecture.md + ADRs; README status/roadmap/how-it-works; small committed fixture APK so fresh clones can probe; unify script wording.

## Virtual filesystem (decided 2026-10)
- Seam: `tartine.runtime.Vfs` maps guest absolute paths to host paths; unmapped paths resolve to `null` and the future java.io/java.nio.file guest bridge must fail closed (deny), never fall back to the host cwd.
- Root = app data, not config: Windows `%LOCALAPPDATA%\Tartine`, macOS `~/Library/Application Support/Tartine`, Linux `$XDG_DATA_HOME/tartine` (default `~/.local/share/tartine`); `TARTINE_HOME` env or `tartine.home` property override everything.
- Guest mounts (longest prefix wins): `/data/data/<pkg>` and `/data/user/0/<pkg>` (incl. `files|cache|databases|shared_prefs`) → `<root>/data/<pkg>`; `/data/app/<pkg>` → `<root>/apps/<pkg>` (installed `base.apk` / guest-visible sourceDir); `/sdcard` and `/storage/emulated/0` → the desktop user's real home directory, mounted read-write Wine-style; `/data/local/tmp` → `<root>/tmp`. `/system`, `/proc`, `/dev`... stay unmapped.
- Traversal (`..`) and Windows-unsafe segments (drive letters, reserved device names, `:` streams) are denied at the seam (tested in `VfsTest`).

## Graphics ("windows") mapping
- Android path, bottom-up: `Canvas` (Skia 2D) / GLES-via-EGL(`ANativeWindow`) / Vulkan → `Surface` (BufferQueue producer) → `SurfaceFlinger` (VSync-driven system compositor, HWC/OpenGL) → display. `WindowManager` owns Window/View lifecycle, z-order, transforms, and hands layers (`Surface`+`SurfaceControl`) to SurfaceFlinger. `SurfaceView` gets its own layer (isolated); `TextureView` composites inside app GLES. Spec: `source.android.com/docs/core/graphics/architecture`, `/surfaceflinger-windowmanager`.
- Desktop mapping: reimplement a minimal WindowManager + SurfaceFlinger-lite — one Android Window/Surface maps to one desktop window; bridge BufferQueue/gralloc to desktop buffers; pace frames off desktop VSync (Choreographer equivalent).
- Rendering backend: prefer Skia (same engine backing Android `Canvas`, cross-platform C++) or LWJGL + GLES via ANGLE for the GLES path. Do not use JavaFX as the compositor: it is a widget toolkit at the wrong layer and cannot faithfully host Surfaces/HWC semantics; low-level windowing (GLFW/SDL) + GL/Vulkan is the correct substrate. Audit 2026-10 note: the Java route to Skia is the Skija/JetBrains Skiko bindings (Apache-2.0 family — verify license row before adding to THIRD-PARTY); LWJGL only supplies windowing + GL, not a 2D engine. Threading must be designed before the GUI step: GLFW owns the main thread (and macOS needs `-XstartOnFirstThread`), while Android app code expects its own main Looper thread — pick the bridge (Looper drives the GLFW pump) up front.

## Third-party policy
- Reuse-first: prefer OSS/AOSP over hand-rolled (dexlib2 for DEX, baksmali/apktool CLIs as decode oracles, dex2jar/Enjarify as translation oracles, LWJGL3 for windowing/GLES, AOSP ART/Skia as reference only).
- Download CLI oracles into `tools/` via `mise run fetch-tools` (gitignored, never on the runtime classpath); record version + URL + license in `THIRD-PARTY.md`. Compile deps are declared in `build.gradle` (Maven Central), not vendored.
- Only permissive licenses in the runtime path (Apache-2.0/BSD/MIT); keep license texts, never strip copyrights. Our sources stay `--release 14` regardless of what a vendored jar targets.
